# v0.4.2 Signal Candidate Forensics

Release checkpoint for `xm-gold-ai-trader`, extending the read-only live sample
quality report with signal candidate forensics.

This checkpoint does not change trading logic, strategy thresholds, safety
checks, order routing, or AI annotation behavior.

## Scope

- Extended `scripts/analyze_live_sample_quality.py`.
- Added `signal_candidate_forensics` to explain why live bars did or did not
  become final signals.
- Added per-bar diagnostics for:
  - candidate direction
  - confidence when recorded
  - signal reason
  - failed pre-signal rule names
  - execution feasibility blockers
  - selected baseline parameters
  - indicator values where available
  - reconstructed ATR from signal stop distance when possible
  - risk lot forensics for `LOT_BELOW_VOLUME_MIN`
  - broker symbol constraints involved in rejection
- Added aggregate counts for:
  - no candidate generated
  - candidate generated
  - candidate generated but rejected
  - top failed pre-signal conditions
  - top execution feasibility blockers

## Current Findings

Using the current live dry-run sample set:

- total journals: `109`
- unique closed bars: `101`
- final signal count: `0`
- candidate signal count: `1`
- no candidate generated: `100`
- candidate generated but rejected: `1`
- top failed pre-signal condition:
  - `SMA_CROSSOVER_NOT_PRESENT`: `100`
- top execution feasibility blocker:
  - `LOT_BELOW_VOLUME_MIN`: `1`

The only candidate was a `BUY` with confidence `0.55`. It was rejected because
the risk budget produced a computed lot of about `0.00194`, below broker
`volume_min` of `0.01`. The normalized lot remained `0.0`; the system did not
round up to the broker minimum.

Live journals do not store raw fast/slow SMA values. The report marks those
fields as `not_recorded_in_journal`. For the candidate, ATR is reconstructed
from the recorded signal stop distance and selected ATR multiplier.
