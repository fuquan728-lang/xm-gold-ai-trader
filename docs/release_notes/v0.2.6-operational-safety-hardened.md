# v0.2.6 Operational Safety Hardened

Release checkpoint for `xm-gold-ai-trader`, a safe demo-first XM MT5 `GOLD_`
trading scaffold.

This checkpoint does not add AI model trading, does not enable live account
support, and does not enable `order_send` in the default configuration.

## Completed Phases

- Phase 1 safety scaffold: Python 3.11 modules, MT5 connection wrapper, broker
  symbol inspection, baseline signal, risk manager, and demo-first defaults.
- Phase 2 verification contract: pytest isolation, smoke checks, dry-run
  signal checks, preflight checks, and machine-readable JSON outcomes.
- Phase 2.1 manual preflight: manual BUY/SELL `order_check`-only workflow with
  explicit SL/TP/lot calculation and no `order_send`.
- Phase 2.2 order_check matrix: BUY/SELL acceptance matrix over multiple stop
  distances, still `order_check` only.
- Phase 2.3 one-shot demo micro order: manually confirmed demo-only order path
  behind explicit config and environment confirmations.
- Phase 2.4 journal audit: demo order journal schema v1 and legacy journal
  handling.
- Phase 2.5 MT5 history reconciliation: accepted demo order journals reconciled
  against current positions and MT5 order/deal history.
- Phase 2.6 operational safety hardening: runtime lock, emergency stop file,
  one-shot daily guard, and project realized daily PnL guard.

## Current Safety Guarantees

- Default config remains safe: `configs/xm_gold_ai_trader.demo.yaml` has
  `execution.allow_order_send: false`.
- Runtime lock prevents overlapping order-capable runs using
  `.runtime/xm_gold_ai_trader.lock`.
- Stale runtime locks can be recovered after a configurable timeout and are
  recorded with `STALE_RUNTIME_LOCK_RECOVERED`.
- Emergency stop file `.runtime/EMERGENCY_STOP` blocks order-capable scripts
  with `EMERGENCY_STOP_FILE_PRESENT`.
- One-shot guard blocks a second accepted project `GOLD_` demo order on the
  same trading day when `execution.one_shot_only: true`.
- Realized daily PnL guard blocks when project-magic `GOLD_` realized loss
  exceeds `risk.max_daily_loss_pct`.
- Demo-only execution requires manual CLI confirmation and environment
  confirmation for the one-shot demo-order config.
- Journal schema v1 records required audit fields for sent, blocked, and
  pre-confirmation outcomes.
- MT5 history reconciliation classifies sent journals as `OPEN_POSITION_MATCHED`,
  `CLOSED_IN_HISTORY`, `SENT_BUT_NOT_FOUND`, `HISTORY_QUERY_FAILED`, or
  `INVALID_SENT_JOURNAL`.
- Blocked outcomes include stable machine-readable `reason_codes`.

## Explicit Non-Goals

- No AI model trading yet.
- No live account support.
- No continuous auto trading.
- No martingale.
- No grid.
- No automatic lot increase after loss.

## Verification Commands

Run these before considering any further execution work:

```powershell
python -m pytest
python scripts\phase2_verify.py
python scripts\demo_lifecycle_report.py --json
python scripts\reconcile_demo_journal.py --json
python scripts\reconcile_mt5_history.py --json
```

Expected behavior:

- `pytest` passes the isolated `tests/` suite.
- `phase2_verify.py` keeps all always-run safety checks at `orders_sent: 0`.
- Lifecycle and journal audit scripts may report legacy journal warnings, but
  sent journals must not be silently skipped.
- MT5 history reconciliation is read-only and must not send orders.
